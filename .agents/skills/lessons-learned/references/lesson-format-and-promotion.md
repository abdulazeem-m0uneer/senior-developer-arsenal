# Lesson Format, Triggers & Promotion

Detail for the `lessons-learned` skill: the line format, what counts as a capture trigger, worked examples, the promotion ladder, and how to load the Active list automatically.

---

## 1. File Layout

```markdown
# Lessons Learned

<!-- Managed by lessons.py. ... -->

## Active
- L001 [sql,migration] hits:2 | 2026-11-04 | Mistake: dropped a column that a report still read | Cause: assumed no reader outside the API | Rule: grep every reader (jobs, reports, views) before dropping a column | Check: grep -rn "<column>" in repo and SQL views

## Archive
- L002 [git] hits:3 | 2026-11-09 | Mistake: force pushed over a teammate's commit | Cause: assumed the branch was mine alone | Rule: push with --force-with-lease | Check: git log origin/<branch>..HEAD before pushing | Promoted: .agents/rules/lessons-promoted.md
```

One lesson per line. Fields are separated by ` | `; the script replaces any `|` in your text with `/`, cuts each field at 200 characters and the tag list at 60. Tags are lowercase stack or area words (`node`, `sql`, `git`, `deploy`, `auth`) so `search` finds them and the session-start ranking can match them against changed files. `Promoted:` is present only on a promoted lesson and names its guard. Project ids start with `L`, global ids with `G`.

Only lines under `## Active` are loaded. A lesson written by hand above the section headers is kept in the file but never loaded; `check` reports it as a problem. The file is read as UTF-8 with undecodable bytes replaced, so a damaged file degrades instead of failing the session; `check` reports such a file and every command that writes it refuses until it is converted, so the bad bytes are never silently replaced. A global ledger that cannot be read is ignored with a note on stderr.

**Writing safely.** Every command that changes a ledger (`add`, `bump`, `archive`, `promote`, `globalize`) holds an exclusive operating-system lock for that ledger while it reads, changes and rewrites it (`flock` on POSIX, `msvcrt.locking` on Windows; the lock file is `.<ledger name>.lock` beside the ledger, so processes with different temp directories still exclude each other; it is left in place, so git-ignore it, for example `.agents/.*.lock`; it falls back to the temp directory when the ledger directory is not writable). Under the same lock, `add`, `bump` and `globalize` append one line to `<ledger stem>.events.jsonl` beside the ledger (beside its target when the ledger is a symlink; date, local time, event, id, tags and the ledger's file name, never a machine path; no lesson text), which `lessons.py metrics` counts per day; days before the log started come from the ledger's dates, which keep only each lesson's last change, and the report says so. `globalize` logs a `move` in both logs; a move is not counted per day, and the project's stub shows in the Moved column. A stub that recurs after its move (`GUARD FAILED`) is named in the report and its logged repeats after the move count in the project's Repeats. A failed log write warns and never fails the command. Commit the project ledger's events log with the ledger, unlike the lock file; it is append-only, so add `*.events.jsonl merge=union` to `.gitattributes` and two branches that each logged a change merge without a conflict. The global ledger's log stays beside the global ledger, outside any repository. The system releases the lock when the process exits, however it exits, so a crash cannot leave a stale lock. A writer that cannot get the lock within 10 seconds exits 2 and writes nothing. The file is replaced in one rename, so a reader never sees half a ledger.

**Secrets.** `add` exits 2 on text that looks like a credential: an assignment to a key, secret, password, token or bearer name; a known format (`sk-...`, `ghp_...` and the other GitHub prefixes, `AKIA...`, `xox?-...`, a three-part JWT, a PEM `-----BEGIN` line); or an unbroken run of 32 or more characters that reads as random (hex longer than 40, or mixed letters and digits with no word-like pieces). File paths, 7 to 40 character git SHAs, UUIDs and long identifiers pass. Limits: a random string in a single letter case with no prefix and no key name beside it can pass, and so can base64 that contains `/`; the filter is a net, not a licence to paste credentials.

## 2. Capture Triggers

| Trigger | Record when | Typical cause field |
| :--- | :--- | :--- |
| User correction | The user redid, reverted, or rejected the work and said why | assumed X without checking Y |
| Confirmed root cause | Rule 0 on failure ended with a verified cause | skipped step Z |
| Failed build or test | The failure traces to the agent's own assumption | trusted a stale type, config, or doc |
| Blocker review finding | `[Blocker]` or `[Performance]` on the agent's own change | did not run the check the reviewer ran |
| Claim gate breach | The agent said done or passing without fresh evidence | reported from an earlier run |
| Same tool error twice | A repeated invocation mistake | wrong flag, path, or order |
| Self-detected rework | The agent reverted or redid its own edit | first attempt rested on an unchecked assumption |
| Self-detected false statement | The agent finds an earlier claim was wrong | stated from memory instead of reading the file |
| Lesson broken again | A loaded lesson was violated | read the lesson but did not apply it: `bump`, and consider promotion |

Do not record: typos, a flaky network, the user's taste ("prefers tabs"), a decision (use `decision-log`), a guess about the cause, or anything naming a person as the fault.

## 3. Writing Good Fields

| Field | Test | Weak | Strong |
| :--- | :--- | :--- | :--- |
| Mistake | Observable, no judgement | was careless with the migration | ran a migration that locked the table for 4 minutes |
| Cause | A false belief or skipped step | didn't think | assumed the table was small; never checked row count |
| Rule | An instruction that would have prevented it | be more careful | check `reltuples` before DDL; use `CONCURRENTLY` above 100k rows |
| Check | A command or observation | review it | `psql -c "select reltuples from pg_class where relname='orders'"` |

If the check is unknown, the script stores `none yet`; filling it in later is the first step of promotion.

---

## 4. Promotion Ladder

Text in a file only works if it is read and obeyed. Mechanical guards work every time. Climb as high as the mistake allows:

1. **A failing test or type error**: encode the mistake as a regression test (`test-every-change`).
2. **A lint rule, CI step, or `quality-gate` check**: the build fails on the pattern.
3. **A hook**: block or warn at the tool call (for example, refuse `git push --force` to a shared branch).
4. **A rule line** in the matching `.agents/rules/<file>.md`, proposed in a pull request.
5. **An `AGENTS.md` line**, only if it applies to most tasks; every line here costs tokens in every session.
6. **Stays a lesson**: low frequency, low cost.

The script does the bookkeeping:

| Command | Effect |
| :--- | :--- |
| `promote <id> --as test` | Prints a `unittest` stub named after the rule, failing with the lesson's check as its message. Marks nothing: adapt it to the project's test framework and make it pass. |
| `promote <id> --guard <path>` | The guard (test, lint config, hook, CI file) exists at `<path>`: the lesson moves to Archive with `Promoted: <path>`. Exits 2 if the path does not exist. |
| `promote <id> --guard <path> --keep-rule` | The guard covers only part of the rule: also appends the rule line (as `promote <id>` does) and stores `Promoted: <path> + rule <rule file>`. Exits 2 without `--guard`. |
| `unguarded [--min N] [LEDGER...]` | Lessons with N or more hits and no guard (see Escalation below: a rules-only `lessons-promoted.md` promotion is none) and no exemption that holds, Active and Archive, from this ledger, the global one and any named ledger, most hits first. A lesson moved by `globalize` is listed once, from the global ledger. |
| `hits [--since 24h]` | Lesson-guard refusals per lesson in the window (`m`, `h` or `d`), from the hit log. |
| `exempt <id> --reason R` | No mechanical guard fits: stores `Promoted: exempt@<hits>: R`. The lesson stays in its section; `unguarded`, `check`, the session-start header and the retro stop flagging it while its hits stay at that count. A recurrence prints `EXEMPT <id> recurred` and flags it again everywhere until it gets a guard or is exempted again (which records the new count). Refused without a reason, for a secret-looking reason, and for a lesson that already has a guard. `--until YYYY-MM-DD` (a date after today) makes it a pending exemption, `exempt@<hits>: until <date>; R`, for a guard that is planned but not built: it holds through that day, then the next repeat escalates again, and `unguarded` lists it with `(exempt until <date>)` meanwhile. |
| `promote <id>` | Rung 4: appends the rule, its check and the lesson id to `rules/lessons-promoted.md` beside the ledger (`.agents/rules/` for the project ledger, `~/.agents/rules/` for the global one; `--rules-dir` overrides), creating the file with `trigger: always_on` frontmatter, and marks the lesson promoted. Review the wording, change the trigger to `glob` with `globs` if it concerns one stack, and commit it. Agents that do not read `.agents/rules/` need the file wired in through their own rules mechanism or one line in `AGENTS.md`. |

A promoted lesson is no longer injected at session start. If the mistake happens again (`add` of a matching lesson, or `bump`), it returns to Active, keeps its `Promoted:` field, and the script prints `GUARD FAILED` with the guard's path: the guard did not hold and is what needs fixing. `check` lists un-promoted lessons at three hits as candidates (`--min N` or `$LESSONS_PROMOTE_AT` changes the threshold for `check`, `unguarded` and the `PROMOTE` hint), and recurred promoted ones separately. Mention the guard in the commit message so the history explains why the lesson left Active.

**Escalation (exit 3).** A lesson has a guard when its `Promoted:` field names a path other than a rules-only `lessons-promoted.md` file and other than an `exempt@` mark (`<path> + rule <rule file>` from `--keep-rule` is guarded by `<path>`); escalation, `unguarded` and the session-start "Repeats without a guard" note use this one rule (`has_guard`). A repeat that brings a lesson with no guard and no exemption to the threshold or more (`$LESSONS_PROMOTE_AT`, default 3) is saved first: the ledger and the events log are written and `LEARNED` is printed as for any repeat. The script then prints `ESCALATE <id> x<hits>: this lesson has repeated without a guard. Attach one (promote <id> --guard PATH) or record why none fits (exempt <id> --reason ...); every further repeat stops here until then.` on stderr and exits 3. This holds for `bump` and for an `add` that counts as a duplicate. A first `add` never escalates; a lesson with a guard or an exemption exits 0 and keeps its `GUARD FAILED` or `EXEMPT <id> recurred` hint. `ci_learn.py` (ci-wait skill) prints the same `ESCALATE` line when it repeats an unguarded CI lesson, but its exit 3 has its own, wider meaning: recorded and needing a guard whenever it prints `PROMOTE`, `GUARD FAILED` or `EXEMPT <id> recurred`, so a guarded CI lesson that recurs, or a first add with `LESSONS_PROMOTE_AT=1`, exits 3 there too (ci-wait reference, section 7). Exit 3 means recorded: the plugin's Stop gate (`hooks/guard.py track`) and `usage-stats` count a failed lesson command (`lessons.py` or the `lessons` shim) as a recorded lesson when it printed `ESCALATE` or exited 3, whatever the lesson step's redirection or position (`lessons.py` has no other exit 3; a test pins it), so output sent to a file or `2>/dev/null` and a step after `&&` still count; the one misread is another step exiting 3 before an `&&` that then skipped the lesson. When the lesson step decides the exit (it ends the command or only `&&` follows), that exit 3 is no failed check and the steps after its `&&` (a check, a `git push`) never ran and are not recorded; a check that ran before it with `;` still counts as failed, ahead of the lesson. So the caller must not record it again; it attaches the guard or the exemption instead.

### Lesson guard registry

The plugin's `PreToolUse` hook (`hooks/guard_lessons.py`) applies the built-in rules `pgrep-wait-loop`, `pipe-exit`, `calendar`, `hook-bypass`, `help-probe` and `secret-in-message` (and the opt-in `rerun-after-red`, `shell-syntax`, `unseen-hash`, `typed-sha`, `oom-first`, `timer-safety`, `live-script`, `dry-run-chain` and `outer-timeout`), adjusted by `~/.agents/lesson-guards.json` (`$LESSONS_GUARDS_GLOBAL_FILE`) and then the project's `.agents/lesson-guards.json` (searched upward from the project directory; its entry for a built-in rule wins):

```json
{"guards": [
  {"rule": "hook-bypass", "lesson": "G027"},
  {"rule": "help-probe", "enabled": false},
  {"rule": "rerun-after-red", "lesson": "L083"},
  {"rule": "shell-syntax", "lesson": "G008", "min_version": "1.29.0"},
  {"rule": "unseen-hash", "lesson": "G014", "programs": ["send.sh"], "min_version": "1.29.0"},
  {"rule": "typed-sha", "lesson": "G030", "min_version": "1.30.0"},
  {"rule": "oom-first", "lesson": "G040", "min_version": "1.30.0"},
  {"rule": "timer-safety", "lesson": "G051", "min_version": "1.33.0"},
  {"rule": "live-script", "lesson": "G010", "min_version": "1.33.0"},
  {"rule": "dry-run-chain", "lesson": "G007", "programs": ["merge_green.py"], "min_version": "1.33.0"},
  {"rule": "outer-timeout", "lesson": "G013", "programs": ["gate-slot"], "hint": "its --max-wait option", "min_version": "1.33.0"},
  {"rule": "secret-in-message", "lesson": "G021", "programs": ["notify.sh"]},
  {"lesson": "L031", "program": "git", "subcommand": "push", "args_any": ["--force", "-f"],
   "reason": "Force-pushed a shared branch. Push a new branch instead."},
  {"lesson": "G026", "program": "gh", "subcommand": ["pr", "merge"],
   "args_none": ["--match-head-commit", "--disable-auto", "--help", "-h"], "min_version": "1.29.0",
```

`pipe-exit` (built in) refuses a check, a local script or a `git commit` (also `git -C dir commit`; not `git commit --dry-run`, which commits nothing) piped into a later command when the pipeline's status is acted on (`&&`, `||`, `if`/`while`/`until`/`!`, or `$?` read next), unless `set -o pipefail` came first or `${PIPESTATUS[...]}` is read. A commit counts because a hook may refuse it and a filter (`git commit ... | tail`) hides that, so the next push or test runs on the old HEAD; `git commit -m x > log 2>&1; echo rc=$?` and `git log | head` pass.

`wait-on-text` is off until an entry names it (give it `"min_version": "1.33.5"`). It refuses a Bash command with a `while` or `until` loop whose condition (not its body) reads one of the entry's `"paths"` with `grep`, `rg`, `awk`, `sed`, `tail` or `cat` (also `cat f | grep x`): a message file can quote the event it waits for (`MERGED #741`, `Released:`) without the event having happened. `"paths"` is a list of shell globs such as `.agents/bus/inbox-*.md`; a glob with a `/` matches as a path suffix of the argument (absolute, `./` and `$VAR/` spellings too), a glob without one matches the argument's basename. Without `"paths"` nothing is judged. The refusal text is the entry's `"reason"`, default: wait on the authoritative state, e.g. `gh pr view N --json state`, never on message text. A grep of those files outside a loop condition, a loop whose condition reads other files, and a loop body that reads them pass. Not seen: a read inside a command substitution, a redirect (`grep x < file`) or a function. Never raises. See `hooks/guard_wait_on_text.py`.

```json
  {"rule": "wait-on-text", "lesson": "L129", "paths": [".agents/bus/inbox-*.md"], "min_version": "1.33.5"},
```

`durable-path` is off until an entry names it (give it `"min_version": "1.33.5"`). Reusable tools, queued job scripts and repair backups kept in `/tmp` or a session scratchpad are wiped by cleanup or a reboot, so work that is scheduled or persistent must not point there. It refuses (a) a Bash command that schedules work to run later whose script or program path is under those places: `systemd-run` with `--on-calendar`, `--on-active`, `--on-boot`, `--on-startup`, `--on-unit-*` or `--timer-property`; `at` or `batch` reading such a file or text (`at -f /tmp/job.sh`, `echo /tmp/job.sh | at 5pm`, `at ... <<< "/tmp/x.sh"`, `batch < /tmp/job.sh`, a here-document); a crontab installed from stdin (`(crontab -l; echo "0 3 * * * /tmp/x.sh") | crontab -`, also `printf` and `crontab - <<EOF`), and (b) a Write, Edit or MultiEdit of a `.service` unit whose `ExecStart=`, `ExecStartPre=` or `ExecStartPost=` path is under those places, of a crontab file (a name starting with `crontab` or ending in `.cron` or `.crontab`, or a file under `/etc/cron.d` or `/var/spool/cron`; `/etc/crontab` and `/etc/cron.d` files carry a user field, which is skipped) or of an at job file (under `/var/spool/cron/atjobs` or `/var/spool/at`). The path judged is the program, or for an interpreter (`bash`, `python3`, `node`, `env` ...) the script it runs, also inside `bash -c '...'`; a path that is only an argument (`/usr/bin/backup /tmp/data`) passes. "Under those places" is a path under `/tmp/`, one containing `/scratchpad/`, or one matching a glob of the entry's optional `"scratch"` list (at most 50 shell globs; a glob without a leading `/` also matches as a path suffix). Running a script now (`bash /tmp/x.sh`, `systemd-run --scope ... /tmp/x`), `at -l`, `crontab -l` and an echo with no crontab install pass: only scheduled or persistent work is judged. The refusal text names the path and says to keep the script in a durable place; an entry's `"reason"` replaces it. Not seen: a path built from a variable, a script that starts another one from `/tmp`, a crontab installed from a file (`crontab /tmp/lines`: its lines are judged when that file is written), `at` text read from a variable. Never raises. See `hooks/guard_durable_path.py`.

```json
  {"rule": "durable-path", "lesson": "G025", "scratch": ["/var/work/tmp-*/**"], "min_version": "1.33.5"},
```

`tool-result-read` is off until an entry names it (give it `"min_version": "1.33.5"`). When a tool result is too large the harness saves it to a file and prints the path; reading that file loads the whole overflow into the context. It refuses a Read tool call whose `file_path` is inside `<project>/<session>/tool-results/` under `~/.claude/projects/` (any project and session; `~` expanded, `..` and a leading `//` resolved, a relative path taken from the working directory) or matches a glob of the entry's optional `"paths"` list (`~` and `$HOME` expanded; a glob with a `/` matches as a path suffix, one without as a basename pattern; at most 50 globs), for a persisted-output path of another layout. Other files under `~/.claude/projects/` (memory files, transcripts), a file that is merely named `tool-results`, other directory names such as `tool-results-old` and other tools pass. The refusal text says to narrow the query at the source (a filter, a smaller query, an extraction prompt); an entry's `"reason"` replaces it. Judged in the non-Bash path with `live-script`. A bounded read (offset or limit) is refused too: the lesson is to narrow at the source. Not seen: a symlink into such a directory, a Bash `cat` or `head` of the file, and a persisted path outside `~/.claude/projects/` (for example under `/tmp`) unless a `"paths"` glob names it. Never raises. See `hooks/guard_tool_result_read.py`.

```json
{"guards": [
  {"rule": "tool-result-read", "lesson": "L113", "min_version": "1.33.5"}
]}
```

`unseen-time` is off until an entry names it (give it `"min_version": "1.33.5"`). Clock times in reports and messages that were guessed or converted by hand are wrong often enough to matter. The rule judges the same outbound text as `unseen-hash` (the entry's `programs`, `gh` comment, PR and issue bodies, commit and tag messages, outbound MCP tools, `SendMessage`) and refuses a time HH:MM (00-23:00-59) that no tool result, user text, queued message or attachment of the session shows (never the assistant's own text or tool inputs). An ISO timestamp there with a zone, such as `2026-11-25T16:36:44Z` or `2026-11-25 19:36:44 +0300`, counts as its written time, its UTC time and its time in the machine's own zone on that date, so `date` output and a `mergedAt` field both back a time in either zone. A timestamp in an offset other than Z or the machine's is found by the time it shows. Not judged: a time in an `ETA MM-DD HH:MM` or `ETA HH:MM` clause, a time after `by`, `until`, `before` or `at the latest`, a time in a code span, a fenced block or a URL, and the entry's `allow` words (exact times such as `"10:00"`). The refusal names the time and says to copy it from `date +%H:%M` or the API's timestamp. `window_mb` and `programs` work as for `unseen-hash`. It passes when the transcript is missing, unreadable or slow. See `hooks/guard_unseen_time.py`.

```json
{"guards": [
  {"rule": "unseen-time", "lesson": "G015", "programs": ["send.sh"], "min_version": "1.33.5"}
]}
```

`shell-syntax` is off until an entry names it. It refuses a Bash command that the shell cannot parse, before any part of it runs: an apostrophe inside a single-quoted argument (`echo 'it's done'`) ends the quote early, and in a multi-line command the lines before the error would already have run. The hook runs `<shell> -n` on the command (it parses and executes nothing; bash also gets `-O extglob`), with `"shell"` naming the shell: `bash` by default, or `sh`, `dash`, `zsh`, `ksh` or `mksh`. Set `"shell"` to the shell the agent runs commands in (for example `"zsh"` where the login shell is zsh), because a bash parse can refuse valid zsh syntax such as a glob qualifier (`**/*.py(.)`). The refusal shows the shell's first error line (at most 200 characters) and says to put free text in a file with the Write tool or in a quoted heredoc (`<<'EOF'`), never inline in single quotes. It is judged before the other rules. It never refuses for its own fault: a missing shell, a run over 1 second, a command over 200 KB or an exit that is not a parse error passes the command. The rule came in 1.29.0: give its entry `"min_version": "1.29.0"` so older hooks skip it quietly. `rerun-after-red` is off until an entry names it. It refuses a test, build, lint or check command (the same check as the Stop gate: tool and subcommand, flags and wrappers ignored) or a `git push` (same operands) that failed last in the session, with no later pass, until a cause note was recorded after the failure: `python3 scripts/lessons.py cause "<failing assertion or check>: <cause or unknown>"` (both sides required; the note writes nothing, the hook sees it ran). A different command, a passed check and the note command itself are never refused. `unseen-hash` is off until an entry names it; give that entry `"min_version": "1.29.0"`, the first release with the rule, so an older hook skips it quietly. It judges the same outbound text as `calendar` (its own `programs` adds message commands), except that for `git commit` and `git tag` only the message counts (`-m`, `--message`, `-am`, and a here-document only when it carries the message: `-F -`, `--file=-`, or inside the `-m` value as `-m "$(cat <<'EOF' ...)"`; for gh and a message program, a here-document counts when it reaches that command's stdin, directly or through a pipe, or sits inside one of its arguments; a here-document that goes only to another command in the same call is not judged, but when one reaches a message command every body of the call is judged, since the bodies are not split per command): git's own operands such as `git tag --contains <sha>`, `--fixup=<sha>`, `-C <sha>` or a tag target are not judged, since git checks them. The same holds for gh's `--match-head-commit <sha>` and `--target <sha>`, which GitHub checks. Its `programs` match a script run by a shell (`bash .agents/bus/send.sh`, `sh path/send.sh`) by the script's name, and a program word set earlier in the same command line (`S=./send.sh; $S ...`, `S=/srv/repo/send.sh && "$S" ...`, `export S=...`); `bash -c '...'` is code, not a script. The same holds for `calendar`; `secret-in-message` reads the words after `-c` too, since a literal secret there is refused either way. Every commit-like hash in that text must have reached the session from outside the model first: 7 to 40 lowercase hex characters (git and gh print lowercase, so an uppercase hex id such as a disk label in a path is not a hash), with at least one digit and one letter (so `deadbeef` and `20261123` pass), not a UUID segment, not part of a longer hex run, not after `#` (a CSS color; a `#` after it, as in `<sha>#L10`, is still checked), not a binary literal (`0b1011`) and not `ed25519`. A hash inside a URL is checked too. Other bare hex ids with a digit and a letter (a build id such as `2026a1b`, a color without `#` such as `ff00ff00`, a number such as `1e10000`) are judged as well: quote them from a tool output, reword them, or list them in the entry's `"allow"` (a list of words, any case, for example `{"rule": "unseen-hash", "lesson": "G014", "allow": ["ff00ff00"], "min_version": "1.29.0"}`). A UUID written without dashes counts as seen when a tool printed it with its dashes. In an MCP tool's input, the values of id fields are not judged (a key that is `id` or ends in `_id`, `-id`, `Id` or `ids`, such as `message_id` or `threadId`; a `sha` or `commit_sha` value is judged): they name a mail, task or page, and the service checks them. The hook reads the session transcript (`transcript_path` in the hook input), only its last `"window_mb"` MB (default 16, also the most; a smaller window reads less). The cap keeps the worst case, 16 hashes searched for in the whole window, inside the 0.2 s budget, which counts the read too; a 64 MB window took about 0.5 s. Inside a subagent the hook input adds `agent_id`, and the agent's own transcript is read instead: `<session>/subagents/agent-<id>.jsonl`, or one folder deeper for a workflow run (at most 256 run folders searched). When it is not found, the call passes. A hash passes when it is a prefix of, or equal to, a hex run (any case) in an entry there that the assistant did not write: a user entry's text (a typed prompt, a subagent's brief, a message from another session, a task notification, the output of the user's own `!` shell command) and its tool results, a `queue-operation` entry (a message queued while the agent was busy) or an `attachment` entry. A short hash of a printed full hash passes. A full hash when only its short form was printed is refused, because the rest was never shown. The assistant's text, thinking and tool inputs, request copies of them (`api-request-blob` entries) and compaction summaries (the model wrote them) never count, nor a refusal by this rule. A hash the agent prints on purpose (`echo`, a file it wrote and read back) counts: the rule catches recall from memory, not evasion. A hash that a git or gh error rejects does not count either, anywhere in that tool result: git echoing a recalled hash does not confirm it. An error line starts with `fatal:`, `error:`, `gh:`, `GraphQL:` or `{"message":` and says `unknown revision`, `bad object`, `no commit found` or the like. A commit subject that only uses those words is not an error line, so its hash still counts. ### Daily repeat check

Run once a day, as a systemd user timer (the session that starts it may end; a timer does not):

```ini
# ~/.config/systemd/user/lessons-check.service
[Service]
Type=oneshot
TimeoutStartSec=120
ExecStart=/bin/sh -c 'L=/path/to/lessons.py; { $L unguarded --min 2 /path/to/other/lessons.md; $L --file /path/to/lessons.md check --min 2; $L hits --since 24h; } > %h/.cache/lessons-daily.txt 2>&1'

# ~/.config/systemd/user/lessons-check.timer
[Timer]
OnCalendar=Mon..Fri 08:30
Persistent=true
[Install]
WantedBy=timers.target
```

Validate before relying on it: `systemd-analyze calendar "Mon..Fri 08:30"` prints the next run, and after `systemctl --user enable --now lessons-check.timer`, `systemctl --user list-timers` must show it. `TimeoutStartSec` bounds a oneshot (`RuntimeMaxSec` does not). With cron: `30 8 * * 1-5 /path/to/lessons.py unguarded --min 2 > ~/.cache/lessons-daily.txt 2>&1`. Post one line (count of unguarded repeats, the top ten by hits, guard refusals of the last day, the path of the full list) where the owners will see it, then route each repeat to the agent or person who owns its area; it is done when `promote <id> --guard <path>` has recorded the guard.

## 5. Loading Automatically

A lesson nobody loads teaches nothing.

- **Plugin install (Claude Code)**: nothing to do. `hooks/hooks.json` runs `lessons.py active --hook` on session startup, resume, clear and compact. The last matters: compaction drops context, and the hook puts the lessons back.
- **Other installs**: add the same to the project's `.claude/settings.json`, with the script path where the skill is installed:

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|resume|clear|compact",
        "hooks": [ { "type": "command",
        "command": "python3 .agents/skills/lessons-learned/scripts/lessons.py active --hook" } ] }
    ]
  }
}
```

- **Agents without hooks**: one line in `AGENTS.md`, "At session start run `python .agents/skills/lessons-learned/scripts/lessons.py active --hook`."
- **Manual**: the user runs `/lessons-learned`.

`--hook` emits the JSON a `SessionStart` hook uses to add context (`hookSpecificOutput.additionalContext`): a short instruction on how the agent records its own mistakes and names a lesson (`Applying ID: rule`) when it changes a decision, then the project's Active lessons, then the global ones under a `Global lessons (every project):` line, or `(no lessons yet)` when both are empty, so a new project still gets the instruction. Plain `active` (no flag) prints every Active lesson as text for manual use.

What `--hook` selects. The host caps `additionalContext` at 10,000 characters and fifteen full-length lessons alone exceed that, so the hook output is limited to 2,000 characters and each lesson is printed brief, `- <id> [tags] x<hits>: <rule>` (plus ` -> <guard>` when promoted), about a quarter of the full line; `show <id>` prints the full line when the rule is not enough:

1. Project and global lessons are ranked separately by steps 2 to 4 and then alternated, project first, so high-hit global lessons never crowd out every project lesson.
2. Within each ledger the three most repeated lessons (two hits or more) come first, whatever the task.
3. The rest are scored against the session's files: the hook reads `cwd` from its stdin JSON (waiting at most half a second for it) and runs `git status --porcelain` and `git log -5 --name-only` there, each with a 1.5 second timeout. A tag that matches a word or file-type of a changed path (`py` counts as `python`, `sql` as `database`, `yml` as `ci`, and so on) scores 3; each matching word of the mistake, rule or check scores 1. Ties go to the newer lesson.
4. Without git, outside a repository, or on a timeout, every score is zero and the order is newest first.
5. Lessons are added in that order while they fit. The header's script path is counted as 160 characters whatever its real length, so the same ledger shows the same lessons wherever arsenal is installed (a path longer than that makes the output longer than 2,000 characters by the difference). If any did not fit, the last line is `(+N more: lessons.py search <words>)`.

The Active cap of 15 per ledger and its eviction rule are unchanged; ranking decides only what a session start shows. The hook never fails the session: on any error it prints nothing and exits 0.

Cost: about 85 tokens for the instruction, plus the script path, plus the lessons that fit, at most 2,000 characters (about 500 tokens) once per session start. On a real ledger pair (15 project and 15 global lessons) the brief format showed 7 lessons in 1,905 characters where full lines showed 5 in 3,543; `search` output for a common word fell from 5,268 to 1,868 characters. Wall time measured on this repository on Linux, 15 lessons, median of 20 runs: 51 ms before ranking existed, 97 ms with it inside a git repository (two git reads), 65 ms outside one.

Not shipped on purpose: a `Stop` hook that forces a reflection every turn. It would spend tokens on turns with nothing to learn and can loop. What the Claude Code plugin ships instead is a conditional gate (`hooks/guard.py`): hooks on the Bash tool silently note each test, build, lint or CI command that exits non-zero, each one that passes, and each successful `lessons.py add` or `bump`; the `Stop` hook then blocks once, with the exact `add` command, only when such a failure has no later passing run of the same check (same tool and subcommand, whatever the flags and paths) and no lesson recorded after it. A turn with nothing to enforce prints nothing, so it costs no context. It cannot loop: it does nothing while `stop_hook_active` is true, and the question is written to the session state before it is shown, so the same failures are never asked about twice; answering that nothing was learned ends it. `ARSENAL_GUARD=off` disables it. Limits: a pipeline that hides the exit code (`pytest | tail`) is not seen as a failure and never counts as a pass, a narrower passing run (`pytest tests/a.py`) clears a wider failed one (`pytest`), and the gate cannot tell a check left red on purpose from a mistake, which is why it asks instead of recording. The self-audit in Step 5 of the skill still covers mistakes that no command reported.

## 6. Team and Global Use

- Commit `.agents/lessons.md` so every agent and teammate shares it; review additions like code.
- The global ledger is personal and lives outside every repository: `$LESSONS_GLOBAL_FILE`, default `~/.agents/lessons.md`. `active` and `search` read it after the project ledger; `add --global` writes to it; `globalize <id>` moves a project lesson there (the project copy is archived with `Promoted: global G###`; a matching global lesson gets the hits instead of a copy). Commands that take an id reach it through a `G` id or `--global`; `check --global` validates it. The script refuses to write a global ledger that sits inside the repository it is run from.
- What belongs there: mistakes about a tool or a habit that would repeat in any repository, such as a git flag, a shell quoting trap, a package manager's behaviour, or reporting a result without running the check. What does not: anything naming this project's files, schema, services, people or conventions; that stays in the project ledger, where the team sees it.
- A global lesson that says the same as an Active project lesson is not shown twice; the project's wording wins.
- Prune: lessons not hit for months and covered by a guard belong in Archive, not Active.

## 7. Measuring It

`evals/task-lesson-recall` checks that a recorded lesson changes behaviour. Its fixture is a small repository where the obvious edit (a generated `config/settings.json`) is the wrong one and `.agents/lessons.md` already says so; the graders pass only if the source template was changed and the generated file regenerated. Run it with the other `task-*` cases (see `CONTRIBUTING.md`); the with-plugin arm gets the lesson from the `SessionStart` hook, the baseline arm does not.
